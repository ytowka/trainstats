# Архитектура синхронизации с сервером (v3)

## Принципы

- **Offline-first**: локальная БД всегда самодостаточна, сервер — транспорт и облачное хранилище.
- **Идемпотентность всех операций**: ретраи/повторы безопасны (дедуп по id).
- **Один цикл синхронизации: push → pull → сохранить lastSeq** (не «или-или»: после нашего push чужие изменения могли уехать вперёд).
- Сервер хранит **только текущее состояние** (без истории) + компактированный курсор изменений (seq).

## Единица синхронизации

**Workout целиком (sets внутри payload) и Exercise.** Сеты отдельно не синхронизируются.
Конфликт-политика: **LWW по целой сущности**, без полевого мержа.

## Время и конфликты

- LWW по **серверному времени**: сервер ставит `lastEdited = server now()` на каждый принятый upsert.
- Порядок push = тотальный (сервер сериализует), гонок нет; семантика — «последний push выигрывает».
- Клиентский `lastEdited` — только UI-метадата, в протоколе сравнения не участвует; часы устройств из протокола исключены.
- v2 (опционально): кламп клиентского `lastEdited` (`min(client_ts, server_now + 5min)`) или HLC — поле в payload уже есть, формат менять не придётся.

## Клиент (Room)

- Сущности `WorkoutEntity`, `ExerciseSetEntity`, `ExerciseEntity` — PK UUID (`String`) ✅ сделано.
- **Две pending-таблицы**: `PendingUpdateWorkout` / `PendingUpdateExercise`;
  общие поля через `@Embedded PendingSend` (паттерн композиции):
  - `rowId: String` — PK записи журнала (UUID, не id сущности!)
  - `op`: UPSERT / DELETE (tombstone)
  - `sendId: String?` — id батча, NULL = не в полёте
  - `payloadJson: String` — **иммутабельный** снапшот сущности на момент изменения
    (клиентский `lastEdited` внутри payload; при apply с сервера НЕ перегенерируется)
- `lastSeq: Long` — серверный seq последнего полученного изменения («тег» клиента).
- Отдельного «флага pending» нет — непустая таблица и есть флаг.
- Правила записи:
  - изменение сущности (**включая правку одного сета внутри workout'а**) + INSERT в pending — **в одной Room-транзакции**;
  - удаления — `op = DELETE` через репозиторий; **не полагаться на ForeignKey CASCADE** (каскад не пишет в outbox; сервер повторит каскад по FK);
  - правка сущности во время полёта push создаёт **новую** строку outbox → уедет следующим батчем (потерь нет);
  - порядок применения везде: **exercises → workouts** (FK RESTRICT на `exerciseId`).

## Push

1. В одной транзакции выбрать записи с `sendId IS NULL` из обеих таблиц, пометить `sendId = batchId`.
2. `POST /sync/push` (Bearer JWT), порядок: exercises → workouts.
3. Сервер, в одной транзакции:
   - **идемпотентный upsert по entityId** (ретрай после потерянного ответа не дублирует);
   - `lastEdited = server now()` на принятую сущность;
   - затронутым сущностям — новый `seq` из per-user счётчика.
4. Ответ: `{acked: [rowId…], newLastSeq}` — **ack поэлементный**, не просто 200 OK.
5. Клиент, в одной транзакции: `DELETE ... WHERE rowId IN (acked)` и сохранить `newLastSeq`.
   - Записи, добавленные во время полёта, не трогаются → гонки нет.
   - Нет ответа / ошибка → ничего не удалять; ретрай следующим циклом (безопасно из-за идемпотентности).

## Pull

1. `GET /sync/pull?since=lastSeq` (Bearer JWT) → строки `WHERE last_modified_seq > since ORDER BY seq` + tombstones (пагинация по seq), порядок: exercises → workouts.
2. Клиент применяет идемпотентно (upsert по id; не откатывать строку на меньший seq), сохраняет `lastSeq = max`.
3. Почему без «длинных цепочек»: `last_modified_seq` — **компактированный курсор**, повторные правки строки двигают её seq вверх. Память сервера = O(сущностей), история не хранится. Это модель Firestore/PowerSync/Couchbase-since.

## Заход в приложение

- Обычный запуск → полный цикл push → pull.
- `lastSeq` отсутствует (новое устройство / чистая установка): полный snapshot с сервера → **мерж поверх локального pending** (не затирание).
- Recovery-путь: повреждение данных / смена схемы → повторный snapshot.

## Сервер

- Таблицы `workouts`, `exercises` (sets сериализованы внутри workout payload) с колонкой `last_modified_seq`; сетам отдельной таблицы/колонки не нужно.
- Per-user монотонный счётчик `seq` (инкремент в той же транзакции, что и запись; присваивает только сервер).
- Tombstone-таблица удалений: `(entity_type: workout|exercise, id, seq)`.
- `userId` — из JWT (до появления auth: заглушка, один тестовый юзер).
- Auth: эндпоинты проектируются сразу под `Authorization: Bearer JWT`; выдача/refresh токенов — следующий этап.

## Этапы внедрения

1. Клиентская БД: две pending-таблицы (`@Embedded PendingSend`) + запись в транзакциях репозиториев (включая DELETE).
2. Сетевой слой: Ktor-клиент, DTO, интерфейс sync API (push/pull) в common-модуле.
3. Сервер: схема + per-user seq-счётчик + идемпотентный push + pull-курсор (тестовый юзер).
4. Sync-оркестратор: цикл push→pull, ack-удаление, lastSeq-хранилище, WorkManager для фона.
5. Snapshot-путь для нового устройства; затем JWT-авторизация.

## Открытые вопросы

- Выдача/refresh JWT, регистрация пользователей — отдельная задача.
- `ExerciseEntity`: синхронизировать только пользовательские упражнения (архивация/кастомные), предустановленные — нет.
- v2 конфликты: кламп `lastEdited` или HLC, если «последний push выигрывает» окажется недостаточно.
